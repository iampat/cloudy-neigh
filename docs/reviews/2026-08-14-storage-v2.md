Ali, let’s dive into [docs/design/storage.md](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/storage.md).

The document is well-reasoned and refreshingly disciplined. Basing durability and linearization entirely on immutable content-addressed objects and conditional creates (`IfNotExist`) eliminates the operational baggage of an external lock manager or Raft cluster.

Here is the architectural review, broken down from first principles.

---

### 1. Initial Assessment & Invariant Deconstruction

* **The Core Invariant:** A single total order over commits established strictly by the object store’s atomic conditional create on `wal/<seq>`.
* **The Elegance:** Decoupling bulk payload uploads (step 1: parallel, content-addressed, zero contention) from metadata sequencing (step 4: small serialized commit record).
* **The Core Tension:** You are using S3/GCS as a low-cost, decentralized consensus engine. Because object storage metadata round trips are high-latency ($30\text{–}100\text{ ms}$) and priced per API call, this architecture excels at batch-oriented workloads with low writer-process contention, but will strain under uncoordinated multi-writer contention or high-frequency single-key writes.

---

### 2. Back-of-the-Envelope Sanity Checks

Let's put hard numbers to the system bounds:

1. **Commit Ceiling & Slot Contention:**
   * Single-slot serialization limit: At $50\text{ ms}$ average RTT for a conditional `PUT`, the maximum throughput for a single sequential WAL stream is:
     $$\frac{1}{0.050\text{ s}} \approx 20\text{ commits/s}$$
   * With $N$ concurrent writer processes competing for `wal/<seq>`:
     * 1 winner succeeds in $1\text{ RTT}$ ($50\text{ ms}$).
     * $N-1$ losers fail ($50\text{ ms}$), issue a `GET` for the winner’s record ($30\text{ ms}$), re-apply, and retry `wal/<seq+1>` ($50\text{ ms}$).
     * At $N = 5\text{ active processes}$, a loser pays $\ge 130\text{–}200\text{ ms}$ tail latency per collision. Contention scales quadratically in total API calls without jittered backoff or local batching.

2. **Shard Write Amplification at 100M Scale:**
   * $100\text{M documents} \times 250\text{ B/entry} \approx 25\text{ GiB}$ total manifest data.
   * At $1\text{ MiB}$ per shard $\approx 25,000\text{ shards}$ (each holding $\sim 4,000\text{ entries}$).
   * If a batch updates $1,000$ keys with a **uniform random key distribution** (e.g., UUIDs or hashes), those $1,000$ updates land across $\sim 980$ distinct shards.
   * Materializing that checkpoint requires writing $980 \times 1\text{ MiB} \approx 980\text{ MiB}$ of new shard blobs to S3/GCS.
   * Updating $200\text{ KB}$ of key data generates $\sim 1\text{ GB}$ of checkpoint I/O (**$\sim 5,000\times$ write amplification**).

3. **In-Memory Footprint & Startup Latency:**
   * At $100\text{M}$ documents, the $35\text{ GiB}$ resident map requires substantial memory on every node.
   * At restart, deserializing a $2.5\text{ MiB}$ root manifest is fast ($\sim 10\text{ ms}$), but warming or scanning $25\text{ GiB}$ of shards over the network will bottleneck cold start times unless shards are loaded strictly on demand behind an LRU cache.

---

### 3. Pragmatic Architecture & Trade-Off Analysis

#### A. Read-Path Verification (`CONSIDER(ali)` on line 335)
* **The Math:** Hardware-accelerated SHA-256 processes $\sim 2\text{ GB/s}$ per core ($5\text{ ms}$ per $10\text{ MiB}$ blob).
* **Assessment:** At $10\text{ MiB}$ over WAN, network transfer ($50\text{–}100\text{ ms}$) dominates CPU time, so SHA-256 verification is fine for cold network fetches. However, if you introduce an in-memory or NVMe block cache later, $5\text{ ms}$ of CPU per read will cap a single core at $200\text{ QPS}$.
* **Recommendation:** Keep digest verification on every fetch from remote storage (bit-rot + provider corruption defense). Bypass it on reads served out of a verified local cache.

#### B. Storage Leaks / Orphan Blobs
* Step 1 writes blobs before step 4 commits them. If a writer crashes after step 1 or cancels due to timeout/context cancellation, those blobs are orphaned immediately.
* **Recommendation:** Note in the document that GC / sweeper marks blobs strictly from reachable checkpoint trees + active WAL records. Orphaned blobs are an accepted cost of lockless parallel ingestion, but lifecycle policies or GC must be budgeted.

#### C. `fileblob` Divergence
* The doc accurately acknowledges that `fileblob`'s `IfNotExist` has a stat-then-rename race.
* **Recommendation:** Make sure integration tests that test multi-process races run against `memblob` or a local S3-compatible mock (e.g., MinIO), rather than relying on `fileblob`.

---

### 4. Failure Modes & What Breaks First

1. **The Writer Convoy / Optimistic Contention Spike:**
   * *Trigger:* A burst of small writes from multiple independent processes.
   * *Symptom:* Slot collisions cascade. Losers repeatedly fetch WAL records to catch up, multiplying S3 API requests and blowing out commit latency.
2. **Random-Write Checkpoint Storm:**
   * *Trigger:* Write workloads that touch non-contiguous keys across the keyspace.
   * *Symptom:* The number of dirty shards approaches the number of updated documents, resulting in gigabytes of shard uploads per checkpoint interval $T$.
3. **Tail Probe Lag in Read-Heavy Nodes:**
   * *Trigger:* Reader-only nodes polling `wal/<applied+1>` on a fixed interval cadence.
   * *Symptom:* If a writer commits 50 batches in a burst, the reader issues 50 sequential round trips to advance its tail unless batch probing (`wal/` range/prefix listing or multi-step lookahead) is allowed.

---

### 5. Sparring Questions

To sharpen the design and finalize this revision:

1. **Writer Topology:** Are you expecting multiple independent writer processes in production to compete for the same bucket simultaneously, or is there usually a single primary/leader writer process per namespace with multiple read replicas?
2. **Key Locality:** Are user keys naturally hierarchical/prefixed (e.g., `/users/123/items/...`), or uniform random hashes/UUIDs? (If keys share common prefixes, key-range sharding limits dirty shard fan-out dramatically).
3. **Replay & Startup Strategy at 100M Keys:** Is the plan for the resident map to load all $25\text{ GiB}$ of shards eagerly at startup, or will index lookups perform two-level lookups (root manifest in RAM $\to$ lazy shard fetch from cache/blob)?
