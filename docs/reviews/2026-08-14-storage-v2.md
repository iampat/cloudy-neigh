### 2. Back-of-the-Envelope Sanity Checks

Let's put hard numbers to the system bounds:

1. **Commit Ceiling & Slot Contention:**
   * Single-slot serialization limit: At $50\text{ ms}$ average RTT for a conditional `PUT`, the maximum throughput for a single sequential WAL stream is:
     $$\frac{1}{0.050\text{ s}} \approx 20\text{ commits/s}$$
   * With $N$ concurrent writer processes competing for `wal/<seq>`:
     * 1 winner succeeds in $1\text{ RTT}$ ($50\text{ ms}$).
     * $N-1$ losers fail ($50\text{ ms}$), issue a `GET` for the winner’s record ($30\text{ ms}$), re-apply, and retry `wal/<seq+1>` ($50\text{ ms}$).
     * At $N = 5\text{ active processes}$, a loser pays $\ge 130\text{–}200\text{ ms}$ tail latency per collision. Contention scales quadratically in total API calls without jittered backoff or local batching.

2. **Shard Write Amplification at 100M Scale:**
   * $100\text{M documents} \times 250\text{ B/entry} \approx 25\text{ GiB}$ total manifest data.
   * At $1\text{ MiB}$ per shard $\approx 25,000\text{ shards}$ (each holding $\sim 4,000\text{ entries}$).
   * If a batch updates $1,000$ keys with a **uniform random key distribution** (e.g., UUIDs or hashes), those $1,000$ updates land across $\sim 980$ distinct shards.
   * Materializing that checkpoint requires writing $980 \times 1\text{ MiB} \approx 980\text{ MiB}$ of new shard blobs to S3/GCS.
   * Updating $200\text{ KB}$ of key data generates $\sim 1\text{ GB}$ of checkpoint I/O (**$\sim 5,000\times$ write amplification**).

3. **In-Memory Footprint & Startup Latency:**
   * At $100\text{M}$ documents, the $35\text{ GiB}$ resident map requires substantial memory on every node.
   * At restart, deserializing a $2.5\text{ MiB}$ root manifest is fast ($\sim 10\text{ ms}$), but warming or scanning $25\text{ GiB}$ of shards over the network will bottleneck cold start times unless shards are loaded strictly on demand behind an LRU cache.

### 3. Pragmatic Architecture & Trade-Off Analysis

### 4. Failure Modes & What Breaks First

1. **The Writer Convoy / Optimistic Contention Spike:**
   * *Trigger:* A burst of small writes from multiple independent processes.
   * *Symptom:* Slot collisions cascade. Losers repeatedly fetch WAL records to catch up, multiplying S3 API requests and blowing out commit latency.
2. **Random-Write Checkpoint Storm:**
   * *Trigger:* Write workloads that touch non-contiguous keys across the keyspace.
   * *Symptom:* The number of dirty shards approaches the number of updated documents, resulting in gigabytes of shard uploads per checkpoint interval $T$.
3. **Tail Probe Lag in Read-Heavy Nodes:**
   * *Trigger:* Reader-only nodes polling `wal/<applied+1>` on a fixed interval cadence.
   * *Symptom:* If a writer commits 50 batches in a burst, the reader issues 50 sequential round trips to advance its tail unless batch probing (`wal/` range/prefix listing or multi-step lookahead) is allowed.

### 3. Pragmatic Adjustments to the Architecture

1. **Two-Level Manifest Index with Shard Paging:**
   * Do not load all shards into memory at startup. Keep only the Root Manifest and Bloom Filters in RAM.
   * Fetch and parse $1\text{ MiB}$ shards lazily on cache miss, and evict using an in-memory LRU.
2. **Backoff with Full Jitter on Lost Slots:**
   * When two processes race for `wal/<seq>`, the loser must not immediately hammer `wal/<seq+1>`.
   * Apply exponential backoff with full jitter (e.g., $t = \text{random}(0, 2^i \times 20\text{ ms})$) while consuming the winner's record.
3. **Replay Acceleration:**
   * When recovering from a checkpoint, the reader needs to catch up across $K$ WAL records.
   * If $K=100$, probing sequentially takes $100 \times 30\text{ ms} = 3\text{ seconds}$. Allow the recovery path to issue a bounded prefix listing (`ListObjectsV2` on `wal/` starting at `checkpoint_seq + 1`) to fetch all outstanding WAL filenames in a single round trip.

### 1. Initial Assessment & Invariant Deconstruction

Two critical engineering problems are in front of us:
1. **CAS Stability with Protobuf:** Protobuf was explicitly designed *not* to guarantee byte-for-byte canonical output across library versions, toolchains, or architectures. If the content digest ($H(b)$) depends on Protobuf serialization, any subtle serialization drift threatens deduplication and tree validation.
2. **Recovery Budget (SLA of a "few seconds"):** Bounding the recovery window to $< 3\text{ seconds}$ at $100\text{M}$ documents requires decoupling WAL replay from sequential round trips.

---

### 2. How to Make CAS Stable with Protobuf

The official Protocol Buffers specification explicitly states: *"Deterministic serialization only guarantees the same byte stream for a single binary build, not across compiler versions, languages, or architectures."*

To make Protobuf rock-solid for Content-Addressable Storage (CAS), follow these **four canonical rules**:

```protobuf
// Good: Deterministic, canonical, zero map ambiguity
message ManifestShard {
  // Repeated entries strictly sorted by key in ascending byte order
  repeated ManifestEntry entries = 1; 
}

message ManifestEntry {
  bytes key = 1;         // Binary key (lexicographically sorted)
  bytes digest = 2;      // 32-byte SHA-256
  int64 size_bytes = 3;  // Document size
  int64 version = 4;     // Monotonic version / sequence
}
```

#### The 4 Invariants of Canonical Protobuf CAS:
1. **Ban Protobuf `map<K, V>` in Hashed Messages:**
   * Go runtime map iteration is deliberately randomized. While `proto.MarshalOptions{Deterministic: true}` sorts maps, cross-language or future runtime updates can sort UTF-8 vs. raw bytes differently.
   * **The Rule:** Use `repeated Entry` instead of `map`. The writer must explicitly sort `entries` by `bytes key` (via `bytes.Compare`) before marshaling.
2. **Always Use Ascending Tag Numbers:**
   * Field tags must appear in strictly ascending order ($1, 2, 3, \dots$).
3. **Explicitly Strip Unknown Fields & Default Zero-Values:**
   * Before hashing, discard unknown fields (`proto.DiscardUnknown(msg)`) so an upgraded client adding a field doesn't break digest compatibility with older readers.
4. **Deterministic Marshaler Option in Go:**
   * Always write:
     ```go
     var CanonicalMarshal = proto.MarshalOptions{
         Deterministic: true,
         AllowPartial:  false,
     }
     ```

> **Alternative (Even simpler & faster):** For $1\text{ MiB}$ manifest shards, consider a **flat binary index block** (like SSTable / LevelDB data blocks):
> `[entry_count: uint32] [offsets: uint32...] [key_len: uint16, key, digest: 32B...]`
> * **Pros:** Zero serialization ambiguity, byte-for-byte canonical, and allows **in-memory binary search directly on the raw bytes** without decoding the whole shard into Go structs!

### 3. Back-of-the-Envelope on Recovery SLA ($K$ vs. Few Seconds)

A recovery SLA of **$\approx 2\text{–}3\text{ seconds}$** is well-balanced. Let’s calibrate the knobs ($K$ = max WAL records between checkpoints):

```
Sequential Replay (Bad):
  K = 100 records × 30 ms (S3 GET RTT) = 3.0 seconds

Parallel Replay (Good):
  1. ListObjectsV2 on `wal/` from checkpoint_seq + 1  ──>  1 RTT (~50 ms)

```

* **Recommended Defaults:**
  * $K = 200\text{ commits}$ (or $T = 15\text{ seconds}$, whichever comes first).
  * Startup lists `wal/` with a prefix filter, downloads un-checkpointed WAL records in parallel, and applies them sequentially.
  * **Result:** Cold-start recovery takes **$< 500\text{ ms}$**, comfortably inside your SLA.

### 2. Implementation Blueprint for the Local Lock

To ensure the storage engine remains portable and clean:

```go
type Committer struct {
    bucket *blob.Bucket
    mu     sync.Mutex // Serializes local goroutines for memblob/fileblob
    // ...
}

func (c *Committer) Commit(ctx context.Context, batch *Batch) (*CommitResult, error) {
    // 1. Upload immutable blobs in parallel (no lock needed)
    if err := c.uploadBlobs(ctx, batch); err != nil {
        return nil, err
    }

    // 2. Local serialization (fast path for fileblob/memblob, group commit queue for prod)
    c.mu.Lock()
    defer c.mu.Unlock()

    // 3. Conditional create loop on wal/<seq>
    for {
        err := c.tryWriteWAL(ctx, nextSeq, batchRecord)
        if err == nil {
            // Won the slot
            return c.applyLocal(batchRecord), nil
        }
        if errors.Is(err, cas.ErrSlotTaken) {
            // Lost slot: catch up & retry
            c.catchUpTail(ctx)
            continue
        }
        return nil, err
    }
}
```
