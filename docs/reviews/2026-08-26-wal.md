2. **Cold-Start Segment Overwrite on Purged Streams (Critical Invariant Violation):** In [`Append`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L143-L157), `lastKnown` starts uninitialized ($0$), so the writer unconditionally targets `seq = 1`. 3. **In-Process Lockstep Contention:** Without local synchronization inside `Log`, multiple goroutines in the same binary appending to the same stream issue concurrent WAN conditional creates to S3/GCS, colliding with themselves and burning billable Class A mutations.
4. **Read Heap Allocation Blowup:** Copying each record individually out of the [`recordio`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/recordio.md) scanner incurs $N$ heap allocations per segment. ## 3. Deep Dive: Critical Correctness & Liveness Defects

### 3.1 The Lagging Writer "Tail Storm" Livelock

Let's analyze the retry loop in [`Append`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L143-L157):

```text
conflicts = conflicts + 1
conflicts < 3             ──▶  seq = seq + 1
otherwise                 ──▶  seq = max(seq + 1, Tail(stream) + 1)
                               conflicts = 0
wait a short random time, then continue
```

#### The Math of the Livelock
Suppose Stream $S$ has an aggregate throughput of $R$ appends/second from one or more active writers. Writer $B$ wakes up after an idle period, holding a stale sequence counter.

1. Writer $B$ attempts `Put(seq)` and receives `ErrPreconditionFailed` ($t_0$).
2. Writer $B$ attempts `seq + 1` and `seq + 2`, both returning `ErrPreconditionFailed` ($t_0 + 60\text{ms}$).
3. On the 3rd conflict, Writer $B$ triggers `Tail(stream)`.
4. At $N = 10,000$ segments, `Tail()` executes $\sim 15$ serial probes ($15 \times 30\text{ms} = 450\text{ms}$). At $N = 1,000,000$ segments, it executes $31$ serial probes ($31 \times 30\text{ms} = 930\text{ms}$).
5. During those $930\text{ms}$, the active writers commit $\Delta = R \times 0.93\text{ seconds}$ new segments.
6. `Tail()` returns head $T_{\text{snapshot}}$. Writer $B$ sets `seq = max(seq + 1, T_snapshot + 1) = T_snapshot + 1`.
7. Writer $B$ now tries to append at $T_{\text{snapshot}} + 1$.
   - If $\Delta \ge 3$, sequences $T_{\text{snapshot}} + 1$, $T_{\text{snapshot}} + 2$, and $T_{\text{snapshot}} + 3$ **have already been committed by the other writers**.
   - Writer $B$ hits 3 consecutive 412 conflicts in $\sim 90\text{ms}$.
   - `conflicts == 3` triggers **again**, launching another `Tail(stream)`!

$$\text{Critical Livelock Threshold: } R \ge \frac{3}{\text{Latency}(\text{Tail})} \approx \frac{3}{0.93\text{s}} \approx 3.2\text{ appends/sec}$$

**Result:** At any write rate above **3.2 to 7 appends per second**, a lagging writer can mathematically never catch up to the head of the stream. It stays trapped in an infinite `Tail()` loop, issuing 30 `List` RPCs every second until its `context.DeadlineExceeded` fires.

#### The False-Alarm Penalty under Active Contention
Even when no writer is lagging, if $W = 4$ active writers concurrently compete at the head:
- By the Pigeonhole Principle, at least one writer will lose 3 consecutive attempts on $N+1, N+2, N+3$.
- That writer, although **zero segments behind**, assumes it has drifted, abandons its $+1$ march, and fires a 30-probe `Tail()` search.
- 4 concurrent writers will easily trigger periodic 30-probe `Tail()` storms against the bucket, driving up API costs and inducing 503 Slow Down rate limits on S3/GCS.

#### The Fix
Differentiate between **drift** (thousands of segments behind) and **head contention** (racing at the tip):
1. **Probe ahead before launching full `Tail()`:** When 3 conflicts occur, do not jump straight into a 30-RTT `Tail()`. Issue a single `exists(seq + 16)` probe.
   - If `seq + 16` does *not* exist, the writer is near the head! Do not run `Tail()`; apply exponential backoff and continue the local search.
   - If `seq + 16` *does* exist, the writer has truly drifted. Now, and only now, invoke `Tail()`.
2. **Dynamic / Exponential Conflict Window:** Do not hardcode a constant 3. Let the jump threshold back off ($3, 6, 12$) if `Tail()` was invoked recently.

### 3.2 The Purged Prefix Cold-Start Corruption

In [`Append`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L143-L146):
```text
Append(stream, records):
    encode the batch into one buffer
    seq = lastKnown[stream] + 1
    conflicts = 0
    loop:
```

[`wal.md`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md) relies on the **Contiguity Invariant** ([`wal.md`:L159-L165](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L159-L165)) and carefully documents how [`Tail()`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L264-L269) derives `lo` from data to survive lifecycle purges of $1\dots K$.

**However, [`Append`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L143-L157) has a fatal hole on cold start:**
1. Suppose an operator lifecycle policy purges segments $1\dots 5,000$. The active stream contains segments $5,001\dots 10,000$.
2. A new process starts, initializes `l := logstream.New(store)`, and calls `l.Append(ctx, "main", batch)`.
3. In this new process, `lastKnown["main"]` is $0$.
4. Line 145 sets `seq = lastKnown["main"] + 1 = 1`.
5. The writer executes:
   $$\text{Put}("wal/main/00000000000000000001.recordio", \text{buffer}, \text{Condition}\{\text{Absent: true}\})$$
6. Because segment 1 was purged, **the key is absent**.
7. The conditional create **succeeds**.
8. `lastKnown["main"]` is set to 1.

#### The Consequences
- **Invariant Destroyed:** The stream now contains segment 1, an empty void from $2\dots 5,000$, and segments $5,001\dots 10,000$.
- **Time Inversion:** A record generated in 2026 is physically written to sequence 1, preceding records committed years earlier.
- **`Tail()` Search Corrupted:** The next call to `List("wal/main/", "", 1000)` returns `00000000000000000001.recordio` as its very first key. If the total active segment count is small ($<1,000$), `Tail` returns the last key of that page, but if binary search is entered, the existence of segment 1 and the hole at $2\dots 5,000$ violates binary search assumptions.

#### The Fix
[`Append`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L143-L157) must **never** assume `seq = 1` without consulting the store:
```text
if lastKnown[stream] == 0:
    lastKnown[stream] = Tail(stream)
seq = lastKnown[stream] + 1
```
If the stream is empty, `Tail()` returns 0, and `seq = 1`. If the stream has active segments $5,001\dots 10,000$, `Tail()` returns 10,000, and `seq = 10,001`. The purge gap is never touched.

## 4. Concurrency & Performance Architecture

### 4.1 In-Process Synchronization vs. WAN Stampedes

Line 324 of [`wal.md`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L324) states: *"One `Log` serves many streams. The stream name is a call argument, not constructor state."*

Consider a multi-threaded Go server where 10 worker goroutines append to `"main"` concurrently via `l.Append(...)`:

```text
Goroutine 1 ──┐
Goroutine 2 ──┼──► [ In-Process Log ] ──► WAN HTTP PUT (seq=100) ──► S3 / GCS
...           │                              ▲
Goroutine 10 ─┘                              └── 9 out of 10 fail with 412!
```

If `lastKnown` is unsynchronized:
1. All 10 goroutines read `seq = 100`.
2. All 10 encode their payloads and fire 10 concurrent HTTP PUT requests across the WAN to cloud storage.
3. 1 succeeds; 9 fail with `ErrPreconditionFailed`.
4. The 9 losers retry for `seq = 101`. 1 succeeds; 8 fail...
5. Total network transfers: $\frac{10 \times 11}{2} = 55$ uploads over the WAN to commit 10 batches.

**The Fix:**
Coordinate locally inside the process. Maintain a per-stream mutex (`map[string]*streamState` protected by a `sync.Mutex` or `sync.RWMutex`):
- Goroutines within the same process queue on the stream's local lock.
- Goroutine 1 uploads `seq = 100`. On success, it sets `lastKnown = 100` and releases the lock.
- Goroutine 2 acquires the lock, reads `lastKnown = 100`, and immediately uploads `seq = 101`.
- **Wasted WAN RPCs drop to zero** for all intra-process concurrency. WAN conditional create races are strictly reserved for genuine cross-process competition.

### 4.2 Zero-Allocation Buffer Slicing in `Read`

Lines 333-335 of [`wal.md`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L333-L335) say:
> *"A returned record is an independent copy, because the RecordIO scanner lends a buffer that it reuses."*

If a segment has 1,000 records, calling `scanner.RecordCopy()` inside `Read(ctx, stream, seq)` allocates 1,000 individual byte slices on the Go heap. For a WAL replaying 10,000 segments, this is **$10^7$ heap allocations**, creating massive GC pause times during node startup.

#### The Zero-Allocation Pattern
Because a segment in object storage is fetched as a complete, immutable byte stream, `Read` should not use the incremental `recordio.Scanner`. Instead:
1. Fetch the entire segment into a single contiguous byte buffer: `rawBytes, err := io.ReadAll(body)`.
2. Iterate through the buffer using low-level [`recordio`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/recordio.md) frame header parsing.
3. Slice each [`Record`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L303) as a sub-slice:
   $$\text{records}[i] = \text{rawBytes}[\text{payloadStart} : \text{payloadEnd}]$$

**Allocation Math:**
- Current doc design: $N + 2$ allocations ($N$ record copies + 1 slice header array + 1 read buffer).
- Sub-slice design: **2 allocations** (1 backing buffer + 1 slice header array), regardless of whether $N = 10$ or $N = 10,000$.

### 4.3 S3 / GCS Monotonic Key Hotspotting (Resolving `CONSIDER(ali)`)

In [`wal.md`:L97-L99](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L97-L99), the note says:
> *"CONSIDER(ali): a monotonic key is the classic hotspot shape on S3 and GCS. Appendix B of storage.md names wal/ as a candidate and offers no mitigation for it."*

Here is the engineering reality on S3 and GCS:

2. **S3 Prefix Thresholds:** AWS S3 supports $3,500\text{ PUT/POST/DELETE}$ and $5,500\text{ GET}$ requests per second *per partitioned prefix*.
3. **Partition Hierarchy:** The key format is `wal/<stream>/<seq>.recordio`. Because `<stream>` is part of the prefix, different streams partition independently.

## 5. API & Contract Refinements

### 5.1 Defensive Boundary Validation

Per [`docs/guidelines/go.md`:L37](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/guidelines/go.md#L37) (*"Validate at the boundary, not deep in the call stack"*), [`Append`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L315) and [`Read`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L316) should document explicit boundary rejections:

1. **Empty Batch:** `len(records) == 0` must return a plain error immediately before taking any locks, allocating buffers, or querying the network.
2. **Stream Name Validation:** Stream names must be validated against a strict character set (`[a-zA-Z0-9_-]+`). Slashes (`/`), empty strings (`""`), and path traversal components (`..`) must be rejected. Allowing arbitrary slashes breaks key parsing in `Tail`.
3. **Context Sensitivity in Loops:** The retry loop in `Append` must check `ctx.Err()` at the top of every iteration. A caller whose deadline expired while waiting for backoff must abort cleanly rather than firing another `Put` to the cloud.

### 5.2 Concrete Algorithm: Robust `Append`

Here is the revised, livelock-free, purge-resilient algorithm for [`Append`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L143-L157):

```text
Append(ctx, stream, records):
    if len(records) == 0:
        return 0, fmt.Errorf("logstream: cannot append empty record batch")
    if !isValidStreamName(stream):
        return 0, fmt.Errorf("logstream: invalid stream name %q", stream)
    if err := ctx.Err(); err != nil:
        return 0, err

    buf = encodeRecordIOBatch(records, maxRecordSize)

    state = getOrCreateStreamState(stream)
    state.lock()
    defer state.unlock()

    // Guard against cold-start purge corruption:
    if state.lastKnown == 0:
        head, err = Tail(ctx, stream)
        if err != nil:
            return 0, err
        state.lastKnown = head

    seq = state.lastKnown + 1
    conflicts = 0

    loop:
        if err := ctx.Err(); err != nil:
            return 0, err

        err = store.Put(ctx, key(stream, seq), buf, Condition{Absent: true})
        if err == nil:
            state.lastKnown = seq
            return seq, nil

        if !errors.Is(err, ErrPreconditionFailed):
            return 0, err

        conflicts++
        if conflicts >= 3:
            // Check if we are truly drifting or just contending at the head:
            if exists(ctx, key(stream, seq + 16)):
                // True drift: re-anchor to the head
                head, err = Tail(ctx, stream)
                if err != nil:
                    return 0, err
                seq = max(seq + 1, head + 1)
            else:
                // Head contention: advance sequentially
                seq = seq + 1
            conflicts = 0
        else:
            seq = seq + 1

        sleep(randomJitter(5ms, 25ms))
```

## 2. Breaking Counter-Proposal 1: The Gallop Livelock

### 2.1 The Math: Why Gallop Still Livelocks

Your proposal:
```text
on the 3rd consecutive conflict:
    lo = seq                      # the 412 proved this exists
    d  = 1
    while exists(lo + d):  d = d * 2
    binary search (lo + d/2, lo + d] for the last that exists
    seq = that + 1
```

You noted: *"At W=4 head contention that is 4 probes, not 30... the livelock threshold moves out by roughly an order of magnitude."*

Let's run the latency math for a writer lagging behind an active stream by $\Delta$ segments:
- **Exponential Phase:** Probes $d = 1, 2, 4, \dots, 2^{\lceil\log_2 \Delta\rceil}$. Number of probes $= \log_2 \Delta + 1$.
- **Binary Search Phase:** Search interval of width $\Delta / 2$. Number of probes $= \log_2(\Delta / 2) = \log_2 \Delta - 1$.
- **Total Probe Count:** $\approx 2 \log_2 \Delta$ serial network round trips.

Now plug in typical numbers at $30\text{ms}$ per probe:

| Lag ($\Delta$) | Gallop Probes | Gallop Latency ($t_{\text{gallop}}$) | Livelock Threshold ($R \ge 3 / t_{\text{gallop}}$) |
| :--- | :--- | :--- | :--- |
| **50 segments** | 12 probes | $360\text{ ms}$ | **$8.3\text{ appends/sec}$** |
| **200 segments** | 16 probes | $480\text{ ms}$ | **$6.2\text{ appends/sec}$** |
| **1,000 segments** | 20 probes | $600\text{ ms}$ | **$5.0\text{ appends/sec}$** |
| **10,000 segments** | 28 probes | $840\text{ ms}$ | **$3.6\text{ appends/sec}$** |

Notice what happens:
1. While the lagging writer spends $480\text{ms}$ executing its 16 gallop probes, other writers commit $R \times 0.48\text{s}$ segments.
2. If $R = 10\text{ appends/sec}$ (a tiny trickle for a WAL), other writers commit **$4.8 > 3$ segments** while gallop is in flight.
3. The gallop returns `that = T_snapshot`.
4. The writer sets `seq = T_snapshot + 1` and resets `conflicts = 0`.
5. The writer tries $T_{\text{snapshot}} + 1, T_{\text{snapshot}} + 2, T_{\text{snapshot}} + 3$.
6. **All three are already taken by the active writers.**
7. The writer hits 3 consecutive 412 conflicts in $90\text{ms}$.
8. `conflicts == 3` triggers **again**, launching another gallop!

The threshold moved from $3.2\text{ appends/sec}$ to $6.2\text{ appends/sec}$—a factor of **$2\times$**, nowhere near an order of magnitude. At 10 appends/sec, your writer loops until context timeout.

---

### 2.2 The Root Flaw: The Search vs. Runway Asymmetry

Why does this livelock occur?
Because of the **asymmetry** between the cost of the search and the size of the retry runway:
- You spend **16 to 20 network round trips** ($500\text{ms}$) to find the head.
- Then you give yourself only **3 round trips** ($90\text{ms}$) of linear $+1$ attempts before panicking and starting another 20-round-trip search!

If you spend half a second locating the head, you must grant yourself a runway proportional to the search latency (e.g. 16 to 32 linear attempts with jitter) so you can catch up to the few segments written while you were galloping.

---

### 2.3 Why `exists(seq + 16)` is a Gate, Not a Search

You asked: *"Break this. Where does it fail that your exists(seq+16) does not?"*

You viewed `exists(seq + 16)` as an alternative search algorithm. **It is not a search algorithm; it is an admission gate before searching.**

Under $W = 4$ head contention, writers compete on $N+1, N+2, N+3$. 
- In your proposal, the loser hits conflict 3 and immediately executes `exists(lo + 1)`. That probe is a `List` RPC. If `lo + 1` is free, it returns false, and the writer then issues `Put(lo + 1)`. You have turned a 1-RTT append into a 2-RTT append (`List` followed by `Put`) right at the contention point.
- With the `exists(seq + 16)` gate: On the 3rd conflict, the writer probes `seq + 16`. Since the head is only at $N+3$, `seq + 16` does **not** exist. The writer realizes: *"I am not lagging; I am within 16 segments of the head."* 
- **It does not gallop. It does not run `Tail()`.** It simply steps forward with randomized backoff and calls `Put`.

### The Correct Synthesis
Use **both**, because they do different jobs:
1. **The Gate (`seq + 16`):** On 3 consecutive conflicts, check `exists(seq + 16)`. If false, reset conflicts and keep marching with jitter. Zero multi-probe searches under head contention.
2. **The Re-anchor (Gallop):** If `seq + 16` *does* exist, true drift has occurred. Now, gallop from `seq + 16` (not from 1, and not from `seq`). Gallop is strictly superior to [`Tail()`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L229-L244) here because it is $O(\log \Delta)$ rather than $O(\log N)$ and requires no initial 1,000-object `List` page.

## 3. Analysis of Counter-Proposal 2: In-Process Locking & Throughput

Your analysis of Counter-Proposal 2 is mathematically perceptive, but it conflates two different throughput numbers:

### 3.1 Unpacking the "500 to 1,000 Appends/Sec" Ceiling

Line 367 of [`wal.md`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L367) states:
> *"Appends per second, one stream: 500 to 1,000 | conditional-create contention on the number"*

**This ceiling measures the aggregate multi-writer breaking point of S3/GCS conditional creates**, not the throughput of a single process:
- If 50 distributed writer nodes across a cluster attempt uncoordinated appends, once their combined rate reaches 500–1,000 writes/sec, CAS contention collapses the stream into continuous 412 conflicts.
- For a **single process** writing unbatched records sequentially over a $30\text{ms}$ WAN link:
  $$\text{Single-Process Sequential Ceiling} = \frac{1}{\text{RTT}} = \frac{1}{0.030\text{s}} \approx 33\text{ appends/sec}$$

Even if you remove the in-process lock and let 50 goroutines fire concurrent `Put(seq)` calls:
- Goroutine 1 wins sequence $N$.
- The other 49 goroutines fail with 412.
- Then Goroutine 2 wins $N+1$, and 48 fail.
- **Throughput is still strictly capped at 33 appends/sec!**
- The only difference is that without the lock, you burned **$50\times$ more network egress and AWS/GCS API fees** to achieve the exact same 33 appends/sec.

Your document is not lying. Section 9 of [`storage.md`:L800](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/storage.md#L800) already states this explicitly:
> *"Phase 1 (Baseline) Direct Sequential Writers: 1–20 writes/sec per stream"*  
> *"Phase 2 (Congestion Mitigation) Dedicated WALWriter Gateway Service: 1,000+ writes/sec per stream"*

33 appends/sec is the physics of single-client WAN RTT. Reaching 500–1,000 appends/sec in a single process *requires* group commit / micro-batching (turning $M$ appends into 1 PUT).

### 3.2 The Real Hazard: Holding Locks Across I/O

The legitimate problem with holding a `sync.Mutex` across `store.Put` is not the 33 appends/sec ceiling—it is violating [`docs/guidelines/go.md`:L59](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/guidelines/go.md#L59) (*"No I/O under a lock"*):

If S3 suffers a transient stall or network partition, an HTTP request can hang for $5\text{--}15\text{ seconds}$ before timing out. A goroutine holding a `sync.Mutex` during that stall blocks all other goroutines on that stream from observing `ctx.Done()`.

#### The Clean Go Solution (Turnstile / Channel Token)
You can serialize appends per stream **without holding a mutex during I/O**:

```go
type streamState struct {
    mu       sync.Mutex
    lastSeq  uint64
    // A 1-buffered channel acts as an I/O turnstile that respects context cancellation:
    turnstile chan struct{} 
}
```

When an append arrives:
1. Acquire the turnstile token via `select`:
   ```go
   select {
   case state.turnstile <- struct{}{}:
       defer func() { <-state.turnstile }()
   case <-ctx.Done():
       return 0, ctx.Err()
   }
   ```
2. Read and advance `lastSeq` under short mutex locks.
3. Perform the network `store.Put(ctx, ...)` **outside any `sync.Mutex`**.
4. If `ctx` is cancelled while waiting in queue, the caller aborts cleanly without blocking or deadlocking.

**Verdict on Counter-Proposal 2:** Serializing per-stream in v1 is 100% the right engineering choice. Defer group commit to Phase 2, but serialize using a turnstile channel rather than a raw `sync.Mutex` so that context deadlines are strictly respected.

## 4. Partial 4.2: Zero-Allocation `Read`

> *"One buffer sized to the total payload, with each record copied into a disjoint range, gives the same 2 allocations and keeps every checksum. Do you see a reason to hand-roll the parse instead?"*

**No, your approach is superior.**

You are entirely right: hand-rolling frame parsing skips `recordio`'s payload CRC32C verification unless duplicated, which violates DRY and risks bit-rot acceptance.

Sizing one contiguous backing buffer for the segment's verified records, copying each record into disjoint sub-slices of that buffer during scanning, and returning sub-slices:
- Retains 100% of [`recordio`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/recordio.md) header and payload checksum integrity.
- Delivers the exact same **2 heap allocations** per segment read.
- Establishes the documented contract: retaining one [`Record`](file:///Users/ali/workspace/iampat/cloudy-neigh/docs/design/wal.md#L303) keeps the segment's backing buffer alive in memory.

## 5. Summary of Resolutions

1. **Re-anchor Protocol:** Combine the `exists(seq + 16)` drift gate with your $O(\log \Delta)$ Galloping search. The gate stops head-contention false alarms; the gallop speeds up true drift recovery without touching the 1,000-key `List` page.
2. **In-Process Serialization:** Keep per-stream serialization for v1. Reaching $>33\text{ appends/sec}$ per process is physically impossible without group commit. Use a channel-based turnstile to avoid holding a `sync.Mutex` across WAN I/O.
3. **Zero-Allocation Read:** Preallocate a single payload backing buffer; copy validated `recordio` slices into it.
4. **Purge Protection & Validation:** Cold-start purge initialization (`lastKnown = Tail()`) and stream name validation (`[a-zA-Z0-9_-]+`) are locked in.
