Storage abstraction · design note · v2 of this note

A portable atomic blob store, designed read-latency-first

Local POSIX, GCS, and S3 behind one interface. V0/V1 keeps logical paths as storage keys and gets atomic write, write-if-not-exist, and CAS from each backend's native preconditions — every read is one roundtrip. Atomic rename is deliberately deferred: it is the only requirement that forces indirection, and its machinery (a CAS'd manifest) is specified here as V2 future work.

Scope

V0/V1 guarantees three write semantics; rename is V2

The store must provide, portably across local POSIX, GCS, and S3: atomic write, write-if-not-exist, and compare-and-swap, plus plain read, delete, and list. The design rubric's primary criterion is read latency.

Deferred to V2: atomic single rename, atomic multi-object rename (RenameMany), atomic prefix rename, and snapshot-consistent list. These are the only requirements that cannot be met with per-object primitives — each needs a single CAS-able commit point plus read-side indirection, i.e. a manifest. Keeping them out of V0/V1 removes the manifest, its garbage collection, and its write contention entirely, and keeps every read at one roundtrip.

Dependency note: this proposal introduces gocloud.dev/blob as a new dependency of this repo (today's direct deps are bleve, pebble, and fatih/color). It supplies the portable data path (gcsblob, s3blob, fileblob, memblob); the native preconditions below are reached through its As/BeforeWrite escape hatches or the underlying SDKs.

V0/V1 — build now

Direct-keyed store

Logical path = storage key. All atomicity comes from native single-object preconditions. Reads are 1 RTT, always. No manifest, no GC, no cross-writer contention.

V2 — build when rename is real

Manifest namespaces

Per-namespace opt-in: immutable uuid-named blobs + one CAS'd root manifest. Buys RenameMany, cross-key transactions, and snapshot list — at the costs in §V2.

Architecture

One thin layer: five methods, three shims

There is no logical/physical split in V0/V1 — the Store interface is the whole system. Each backend implements the same five methods; only the precondition plumbing differs. Every write returns an opaque Handle (the backend's version token) that CompareAndSwap later takes as its expectation.

semantics

What each operation promises

Write — atomic replace

Write(path, data) → Handle
  1. Readers concurrent with a Write observe the old bytes or the new bytes, never a mixture and never absence. This is native object-store behavior; locally it is temp-file + rename(2) on the same filesystem.
  2. Returns the new object's version token as an opaque Handle.

WriteIfNotExist — exactly one creator

WriteIfNotExist(path, data) → Handle | ErrExists
  1. The backend precondition (DoesNotExist / If-None-Match:* / O_EXCL) arbitrates racing creators; exactly one wins, losers get ErrExists.
  2. The portable gocloud.dev IfNotExist option is racy on fileblob — the local shim must use O_EXCL directly, not the library option.

CompareAndSwap — optimistic concurrency

CompareAndSwap(path, expect Handle, data) → Handle | ErrConflict
  1. Succeeds iff the object's current version token equals expect; otherwise ErrConflict. Read-modify-write loops (read → mutate → CAS → on conflict re-read) give per-key transactions with no further machinery.
  2. Local implementation: take flock, compare the sidecar counter to expect, temp-write + rename + bump counter, release.

Delete and List — native, specified

Delete(path[, expect]) · List(prefix) → iterator
  1. Delete removes the object immediately — there is no garbage and no GC in V0/V1. An optional expect Handle makes it conditional where the backend supports it (native on GCS; on S3 use conditional delete where available, else document the small unguarded window).
  2. List is the backend's native listing: strongly read-after-write consistent on all three backends, but not a point-in-time snapshot — entries created or deleted during pagination may or may not appear. Snapshot listing is a V2 (or application-level, see below) concern.
Composition

What V0/V1 can already build — and what it can't

Buildable now

Distributed lease lock

WriteIfNotExist(lock, {owner, fence, expiry}) to acquire; CAS to renew, steal-after-expiry, and release. Include a fencing token bumped on every acquisition. It is a lease — safety degrades with clock skew — so use it to reduce contention, and keep correctness on CAS of the data itself.

Buildable now

Per-key transactions

CAS is optimistic read-modify-write; no extra machinery. Also: an application-level pointer file (one small CAS'd object listing a published set, e.g. live index segments) gives consistent publish/subscribe over immutable blobs for one namespace — often all the "snapshot" a system needs.

Not buildable

Cross-key atomicity

Atomic visibility across objects requires all of them to flip through one CAS on one object — no protocol over per-object primitives avoids this. Anything needing it (transactions, RenameMany) is V2's manifest by construction.

Rejected

Redirect-based single rename

A tombstone/redirect protocol can fake one atomic rename, but it puts a redirect branch in every read (the rubric forbids it), only works for cooperating readers, and does not compose to N renames. Explicitly rejected for V0/V1 — rename waits for V2.

The rubric criterion

Latency budget: V0/V1 vs V2, in observed roundtrips

Counted as sequential network roundtrips (RTT) observed by the client; parallel calls count once. The V2 column assumes its optimistic parallel read: cache the manifest, then on read issue the blob GET (from the cached mapping) and a conditional GET of the root in parallel — a 304 confirms the blob in hand; only a changed key costs a second hop. Immutable blobs make the stale fetch safe: it can return a superseded version, never torn bytes.

Reading against a read-latency-first rubric: V2's only regression is the just-changed window on strict-fresh reads of governed keys; pinned-snapshot access (the natural pattern for a search index: pin root at open/refresh, then read segments) pays nothing. Ungoverned namespaces stay at a flat 1 RTT forever.

Critical — adopt in V0

Four rules that keep the V2 door open

Choosing direct keys now costs nothing later only if these contract rules hold from day one. Without rules 1–2, V1 silently forecloses V2.

Rule 1

Handle is opaque

In V1 it is secretly an ETag/generation/counter; in V2 it becomes a manifest entry. Callers must not inspect, persist, or compare handles across processes. Enforce with an unexported representation.

Rule 2

No raw bucket keys escape

A storage key embedded in another object, an external system, or a long-lived URL bypasses any future manifest and would be broken by governed rename. All references go through logical paths via the library; signed URLs are documented point-in-time snapshots.

Rule 3

Namespace-scoped API

Constructors and config speak in namespaces (prefixes), not one global bag, so V2 governance can attach per namespace: manifest where rename is needed, direct keys — and 1-RTT reads — everywhere else.

Rule 4

Cutover is a coordinated deploy

The moment a namespace goes under a manifest its blobs must be immutable; one straggling V1-style writer overwriting a direct key corrupts snapshot semantics. Migration per namespace = all writers upgrade, then flip.

future work

V2: manifest namespaces — the commit-pointer machine

When atomic rename, cross-key transactions, or snapshot list become real requirements, build this once — RenameMany, prefix rename, transactions, and snapshot List all fall out of the same mechanism. Per opted-in namespace: data objects become immutable and uuid-named, and one root object holds the manifest (logical path → blob), mutated only by CAS. N renames are then one manifest edit committed by one CAS: N moves · 0 bytes copied · readers see all-or-nothing.

Spec pointDecisionWhy (defects this closes)
Blob naming uuid-named, never content-addressed Content addressing breaks "a fresh Put can't clash" (equal bytes collide), makes CAS return Handle == expect for identical content, and lets dedup re-reference a blob GC is concurrently deleting.
Root on S3 manifest embeds a monotonic sequence number Single-PUT ETags are content MD5s, so byte-identical states repeat ETags — an ABA hole in If-Match. An embedded sequence makes identical bytes impossible, restoring CAS soundness. (GCS generations are monotonic; no issue.)
GC mark-from-root sweep; delete only unreferenced objects older than an age floor ≫ max write duration A grace period for readers is not enough: a writer between Put(B2) and its root CAS looks unreferenced — a sweep without the age floor deletes B2, the CAS still succeeds, and the committed root holds a dangling handle.
Contention shard the root per namespace — knowing the atomicity boundary shrinks to one shard There is no multi-object CAS on GCS/S3: a rename spanning two roots cannot commit atomically. Cross-shard operations must be forbidden by the API, not left to fail subtly.
Delete / List Delete = manifest edit + deferred GC · List = manifest enumeration Governed deletes must not race in-flight readers of the old root; governed List is thereby a true snapshot (and 1 RTT).
Scaling the manifest copy-on-write tree: interior nodes are plain immutable Puts; the root is the only CAS'd object A change rewrites O(depth) small nodes then lands one root CAS. Nodes need no per-node version machinery.
Migration V1 → V2 bootstrap manifest entries pointing at existing direct keys; copy-on-first-write thereafter No bulk data movement; per-namespace, incremental. Rollback requires materializing entries back to logical keys — a one-way-ish door, per namespace.

Cost sheet accepted with V2, per governed namespace: read indirection (mitigated to ~1 RTT as in §latency), writer serialization on the root, staged-object garbage plus the GC above, and the cutover discipline of rule 4.

What you take on

The honest costs of V0/V1

Consistency

No cross-object atomicity

No rename of any kind, no multi-key transactions, no snapshot List. Deliberate: these are V2's manifest. The application-level pointer file covers the common "publish a consistent set" case.

S3 CAS

ETag ABA edge

Byte-identical rewrites repeat ETags, so a stale CAS can succeed after A→B→A. Callers needing strict CAS on S3 should make payloads self-versioning (embed a counter/nonce). GCS and local tokens are monotonic and immune.

Local backend

Single host only

flock + rename semantics are not NFS-safe and not multi-host. The local backend is for dev and single-node deployments; say so in its package doc.

S3-compatibles

Verify preconditions before trusting

Conditional writes are real on AWS S3 (GA 2024). MinIO and other S3-compatible endpoints must be conformance-tested (If-None-Match:*, If-Match) before the CAS shim is enabled on them — a pre-implementation task, not a footnote.
