Ingestion WAL System — Design Document

Status: Prototype Design & Architecture Spec | Target Engine: cloudy-neigh

1. Overview

The ingestion system provides a high-throughput, simple, and clean document ingestion pipeline. It batches client write requests (PUT/UPSERT and DELETE) and flushes them into sequentially numbered Write-Ahead Log (WAL) bin files (e.g. wal/000000000123.wal) stored on cloud object storage or local disk using coordinator-free Compare-And-Swap (CAS) / conditional writes.

2. Core Components

2.1 Mutation Protocol

Mutations are represented as Protobuf messages containing document updates or deletions:

  • PUT / UPSERT: Includes document ID, fields (title, text, embeddings, LSH hashes), and client mutation timestamp.
  • DELETE: Includes document ID tombstone.

2.2 Storage Abstraction (Go Cloud CDK — gocloud.dev/blob)

Storage is built on top of gocloud.dev/blob (Go Cloud Development Kit), providing portable, out-of-the-box support across multiple storage backends:

  • AWS S3: s3://bucket-name
  • Google Cloud Storage (GCS): gs://bucket-name
  • Local Filesystem: file:///path/to/dir (via fileblob)
  • In-Memory: mem:// (via memblob for fast testing)

2.3 Serialization Drivers

The WAL writer supports pluggable serialization drivers:

  • pb.jsonl: JSON-Lines formatted Protobuf messages (human-readable, easy debugging & inspection).
  • pb.bin / recordio: Length-prefixed binary Protobuf record streams (compact, high-performance binary format).

2.3 Batcher & Flushing Mechanics

The batcher aggregates incoming document mutations in memory and triggers a batch flush when any of the following limits is met:

  • Document Count (N): e.g., max 1,000 documents per batch.
  • Time Interval (T): e.g., max 500ms since oldest un-flushed document.
  • Payload Byte Size (B): e.g., max 4MB per batch payload.

2.4 Write Acknowledgment Modes

Mode Behavior Status
1. WAL Durability Write API blocks synchronously until the batch containing the document is flushed & materialized in the WAL storage bin. Implemented in Prototype
2. State / Index Durability Write API blocks until the WAL batch is applied to the index/store state (e.g., segment build complete). Documented for Future Extension

3. Coordinator-Free CAS WAL Sequence Writer

3.1 Claiming Sequence Numbers without a Coordinator

To write WAL bins without a central lock manager or coordinator service:

  1. The writer determines the candidate next sequence number $S$.
  2. The writer attempts a conditional write: WriteIfNotExist("wal/" + formatSeq(S) + ext, batchBytes).
  3. On Success: Sequence $S$ is claimed and committed.
  4. On Conflict (ErrExists): Another concurrent writer claimed $S$. The writer increments to $S+1$ and retries immediately.

3.2 Head Discovery at Scale ($300M+$ Files)

Boundary Design: With 1 WAL flush/sec over 10 years (~315 million files), listing the entire directory would be $O(\text{files})$.

To keep sequence discovery $O(1)$ RTT:

  • Zero-Padded Keys & Lexicographical Range Probing: Sequence keys are zero-padded to 12 digits (000000000123). Storage listing APIs (GCS, S3, local POSIX) support List(prefix="wal/", startAfter=cachedSeq).
  • Local Sequence Cache: Writers cache the highest known sequence $S_{last}$. Discovery probes with startAfter = formatSeq(S_{last}), scanning only the few keys generated since the last write.

4. Structured Logging & Observability

The ingestion engine uses Go's standard log/slog for structured operational logging:

  • Batch Flushes: Logs batch size (docs & bytes), duration, WAL sequence assigned, and file path.
  • CAS Contention: Logs retry count and sequence collisions for debugging concurrency hotspots.
  • Flush Latencies & Performance: Logs execution duration for WAL storage writes to track I/O bottlenecks.

5. Future Extensions

  • Index Catch-Up Worker: Asynchronous index builder reading sequence bins from WAL and applying them to search segments.
  • WAL Garbage Collection / Archiving: Archiving processed WAL bins older than retention window into cold storage.
